# TrackShift: Final Integration Checkpoints

This is the shared end-to-end runbook for integrating Owner A and Owner B work into one TrackShift backend and one UI-facing API.

It begins only after the relevant checkpoints in CHECKPOINTS_RISHABH.md and CHECKPOINTS_TANVEER.md have passed their local acceptance gates.

Reference documents:

- TrackShift AGENTS.md defines the engineering contract, causality, provenance, rule, and claim requirements.
- MODELS.md defines ownership, model IDs, and contracts C1 to C10.
- API.md is the only public surface seen by the UI.
- CHECKPOINTS_TANVEER.md is the Owner B implementation plan.
- CHECKPOINTS_RISHABH.md is the Owner A implementation plan.
- CHECKPOINTS_INTEGRATION.md is this final integration and release plan.

The objective is not to make two laptops serve two unrelated backends. The objective is one consistent TrackShift API that can be exercised in distributed test mode and delivered in self-contained replay or service mode.

---

## 0. Integration principles

1. The UI calls one gateway only. It never calls an Owner A or Owner B laptop directly.
2. API.md is authoritative for public JSON. No integration step invents fields, renames fields, or returns undocumented values.
3. All model hand-offs use C1 to C10. No code imports another owner's internals.
4. The release demo must not rely on a network connection between laptops. The recommended final mode is one host with versioned artifacts and replay files.
5. Distributed laptop mode is for integration testing. It proves provider compatibility before artifacts are consolidated.
6. Every joined value retains provenance, uncertainty, model version, rule snapshot/configuration version, and causal cutoff.
7. A normal-race eligibility failure gates model execution. The gateway returns the documented null or error form instead of attempting a prediction.
8. C3 removes illegal actions before M22, M24, M25, M26, or M27 evaluates them.
9. Any counterfactual uses the frozen decision-time state plus a declared feasible intervention. It never reads future telemetry or realized outcome data.
10. British Grand Prix remains held out of every training and calibration run. It may be used only for final evaluation, replay generation, and the demo.

## 1. Deployment modes

| Mode | Purpose | Topology | UI target | Final-demo suitability |
|---|---|---|---|---|
| Distributed integration | Verify laptop-to-laptop provider compatibility | Owner A provider plus Owner B provider plus gateway | gateway only | No |
| Consolidated service | Interactive final what-if | one host loads all verified artifacts into one FastAPI app | gateway | Yes |
| Replay bundle | Stable demo and UI development | one static bundle generated by the gateway | replay gateway | Yes, preferred fallback |

### 1.1 Distributed integration mode

Owner A and Owner B each run only their owned route modules behind a local provider adapter. The gateway routes by API ownership:

| Provider | Public capabilities supplied to gateway |
|---|---|
| Owner B | meta, validation, track, rules, legal actions, eligibility, pass prediction, segment time, energy state |
| Owner A | battles, battle timeline, rival state, shadow price, plan, simulation, rival policies |
| Gateway | public API prefix, schema validation, route ownership dispatch, response validation, error mapping, replay parity |

The UI sends requests only to the gateway. Provider addresses belong in ignored local integration configuration and are never committed as machine-specific defaults.

### 1.2 Consolidated service mode

One integration host checks out the tagged release, loads all CPU-verified artifacts, and runs all route modules in one process. Provider adapters become in-process calls to the public C1 to C10 interfaces.

This is the recommended interactive demo mode because a laptop disconnect, firewall, local IP change, or remote GPU issue cannot break the presentation.

### 1.3 Replay mode

The replay generator calls the same gateway routes in-process for the chosen demo event and battle. The resulting JSON is byte-identical in shape to live responses. The UI can run entirely against the replay bundle.

## 3. Release identity and branch protocol

### IN-00: Freeze the integration candidate

**Goal:** establish one immutable integration candidate before copying artifacts or debugging cross-laptop behaviour.

### Steps

1. Merge completed owner PRs into main.
2. Create an integration branch and tag the selected commit after acceptance.
3. Freeze API.md, feature registry schema, data registry schema, and rule configuration schema for that candidate.
4. Record the exact git commit in every artifact manifest.
5. Reject an artifact whose commit, feature schema, geometry version, or rule configuration version does not match the candidate.

### Acceptance gates

- Both laptops resolve the same git commit.
- Every provider reports the same API version.
- All required schema versions are listed in one integration manifest.
- No uncommitted local code is needed to serve a route.

### Deliverables

integration release manifest, tagged commit, compatibility report.

## 4. Artifact exchange protocol

### IN-01: Exchange portable artifacts, not environments

**Goal:** both owners can consume each other's work without copying raw data, virtual environments, private paths, or GPU-specific state.

### Required artifact contents

| Artifact | Minimum contents |
|---|---|
| Model artifact | CPU-loadable model or state dictionary, feature schema, model version |
| Calibration artifact | calibration method, fit split, metrics, model reference |
| Rule artifact | rule snapshot, event configuration version, sources, strict-mode result |
| Value artifact | state grid, policy configuration, model/rule versions, seed |
| Validation artifact | metrics, sample sizes, held-out split, assumptions |
| Replay input | event, battle ID, state references, artifact release identity |
| Manifest | git commit, producer, input manifests, schema versions, created time, checksums |

### Rules

- Do not exchange raw telemetry by default.
- Do not exchange Python pickle modules.
- Use CPU-loadable artifacts only.
- Do not claim an artifact is compatible merely because it loads. It must pass contract and replay tests.
- A failed checksum or schema mismatch is a hard integration failure, not a warning.

### Acceptance gates

- Owner A loads Owner B artifact metadata and vice versa.
- All checksums pass after transfer.
- Feature schema order exactly matches its consuming artifact.
- Rule snapshot is explicit for every event-specific result.

## 5. Canonical state assembly

### IN-02: Build one StrategicState at every decision point

**Goal:** ensure planner, simulator, rule engine, and UI describe the same race state.

### Assembly order

1. Resolve StateRef: year, event, session, lap, segment, distance.
2. Load C7 race-control and pit state. If normal-race eligibility is false, stop model execution and return the documented gate.
3. Load C8 pairwise state: time gap, distance gap, relative speed, relative acceleration, gap rate, and causal trailing trends.
4. Load C1 geometry, segment context, C2 baselines, weather, and tyre context.
5. Load C5 energy state: Energy Store distribution, deployment flow, harvest flow, recharge budget, power limit, and envelope regime.
6. Load C3 legal context and C6 eligibility state using the same event rule snapshot.
7. Load C10 rival belief.
8. For a pass request, load C4 only at the requested decision checkpoint.
9. Construct one typed StrategicState and validate it against API.md.
10. Give M22, M24, M26, and the timeline aggregator the same validated state object.

### Required separation

The integration layer keeps these fields separate:

- time gap and distance gap
- relative speed and gap rate
- Energy Store state, deployed energy, harvested energy, and recharge budget
- observed tyre context and inferred tyre-performance state
- historical DRS covariates and 2026 Overtake state
- rule threshold/provenance and modelled eligibility probability
- observed values, inferred values, simulated values, and rule values

### Acceptance gates

- StrategicState round-trips through JSON without field loss.
- No state contains an offline-only field on a live request.
- Every modelled numeric field has provenance and uncertainty when its producer supplies uncertainty.
- Changing the selected action does not change historical input fields.
- Rule snapshot/configuration version is identical across C3, C5, C6, M22, M24, and M26.

## 6. Single gateway API

### IN-03: Expose one public API

**Goal:** present a stable, singular API at one gateway address.

### Public route matrix

| Route | Provider owner | Gateway responsibility |
|---|---|---|
| GET /meta | Owner B | merge release identity, provider health, stubs |
| GET /validation | Owner B | aggregate component and strategic metrics |
| GET /track/{event} | Owner B | validate geometry and rule-line versions |
| GET /rules/{event} | Owner B | expose sourced rule snapshot and config |
| GET /battles | Owner A | validate query and replay parity |
| GET /battles/{battle_id}/timeline | Owner A | assemble C1 to C10 outputs consistently |
| POST /rules/legal_actions | Owner B | validate StrategicState and legal-action schema |
| POST /rules/eligibility | Owner B | validate causal projection and rule version |
| POST /pass/predict | Owner B | enforce checkpoint and feature schema |
| POST /rival/state | Owner A | enforce causal battle window |
| POST /twin/segment_time | Owner B | validate context and power regime |
| POST /twin/energy_state | Owner B | return causal Energy Store flows |
| GET /value/{event}/shadow_price | Owner A | validate state-grid and rule version |
| POST /plan | Owner A | require legal actions and state completeness |
| POST /simulate | Owner A | freeze intervention state and seed |
| GET /simulate/policies | Owner A | return transparent policy registry |

### Gateway rules

1. Every public response follows API.md exactly.
2. The gateway validates provider response schemas before returning them.
3. Provider exceptions are mapped to documented errors only.
4. Provider hostnames, tokens, and ports live in ignored local configuration.
5. Gateway never calculates a combined score. It returns native subsystem results and planner outputs as defined.
6. A provider timeout in distributed mode returns a clear dependency failure. The final replay mode never depends on provider networking.

### Acceptance gates

- UI uses one base URL only.
- Every route is visible at one documented API prefix.
- Every example from API.md validates at the gateway.
- Gateway rejects undocumented input fields unless API.md marks them optional.
- Provider response schema mismatch fails the integration test.

## 7. Cross-laptop test sequence

### IN-04: Prove distributed compatibility

**Goal:** detect contract, serialization, path, and portability issues before release consolidation.

### Steps

1. Start Owner B provider with replay-safe artifacts and health metadata.
2. Start Owner A provider with replay-safe artifacts and health metadata.
3. Configure gateway provider addresses in an ignored local file.
4. Run smoke requests for every public route.
5. Run one full timeline request for a held-out battle.
6. Run legal-actions, eligibility, pass, rival, energy, shadow-price, plan, and simulation requests from the same StateRef.
7. Save request and response fixtures with provider versions.
8. Repeat after restarting providers to prove no hidden in-memory state is required.

### Acceptance gates

- No response includes an absolute path.
- All providers report CPU inference capability.
- Request identifiers and provenance remain unchanged across gateway forwarding.
- Timeline components agree on event, session, lap, segment, rule snapshot, and model version.
- Restarting a provider changes no seeded replay output.

### If output is bad

| Symptom | Likely cause | Fix |
|---|---|---|
| Gateway and provider disagree on field names | contract drift | update API.md first, then regenerate schemas on both sides |
| Planner rejects a state after gateway accepts it | different StrategicState validator | move shared validation into one public module |
| Energy or rule version differs inside timeline | artifacts built against different releases | reject mixed manifest and rebuild from frozen candidate |
| Remote request succeeds but replay fails | hidden provider-only calculation | make replay generator call the same public route code |
| UI needs two URLs | ownership leaked into frontend | route through gateway only |

## 8. End-to-end decision tests

### IN-05: Verify a real decision flow

**Goal:** prove that system components connect causally from observations to an auditable plan.

### Required scenarios

| Scenario | Expected behaviour |
|---|---|
| Normal green-flag following | state assembles, all eligible components answer |
| Safety Car, VSC, yellow, pit, or unknown control | model gate is shown; no invalid plan is produced |
| Detection-line approach | projected gap, eligibility probability, and rule state agree |
| Overtake armed then Activation reached | power envelope changes only through C3 and event rules |
| High deployment request | C3 may remove it before M22 or M24 scores it |
| Low energy state | planner exposes constrained alternatives and regret |
| Post-pass state | counterattack and role switch are considered |
| High uncertainty | planner returns decision stability and risk-sensitive output |
| Historical DRS row | historical covariate is not shown as 2026 Overtake |

### Acceptance gates

- Each scenario has a stable fixture and expected schema.
- No scenario requires future telemetry in a live input.
- Plan, simulator, and timeline use compatible state values.
- All counterfactual fields are labelled SIMULATED or INFERRED as appropriate.

## 9. Validation aggregation

### IN-06: Build one evidence package

**Goal:** give the UI and reviewers meaningful evidence instead of one overall accuracy number.

### Required panels

| Component | Required evidence |
|---|---|
| Pass model | Brier, log loss, calibration, ROC-AUC, PR-AUC, N |
| Rival model | synthetic recovery, predictive likelihood, next-segment metric, stability, calibration, latency |
| Twin and segment transition | MAE, RMSE, speed/segment breakdown, physical violations, energy accounting |
| Eligibility and gap model | next relative-speed and gap errors, Detection-Line projected-gap error, probability calibration |
| Planner | terminal P(ahead), energy, regret, rule violations, CVaR, stability, latency |
| Ablation | energy state, tyre state, gap dynamics, rule state, rival belief, future eligibility |
| Simulator | seed, episode count, assumptions, policy comparison, simulated status |

### Acceptance gates

- Every metric reports sample size and split.
- British Grand Prix is labelled held out.
- Simulated policy results are never presented as observed race outcomes.
- A missing component report makes GET /validation incomplete rather than fabricated.

## 10. Replay bundle and UI hand-off

### IN-07: Produce a self-contained UI package

**Goal:** make the final UI run with no backend or inter-laptop dependency.

### Steps

1. Select release commit, event, battle, direction, rule snapshot, and artifact versions.
2. Call the unified gateway in-process to generate track, rules, battles, timeline, validation, shadow-price, plan, and simulation files.
3. Store checksums and stubs_used in bundle_manifest.
4. Validate replay files against the same schemas as service responses.
5. Give Owner C one bundle root and one API-compatible route map.
6. Render all display obligations from API.md: provenance, uncertainty, rule sources, energy labels, DRS-era distinction, normal-race gate, simulation assumptions, and checkpoint labels.

### Acceptance gates

- Bundle contains zero stubs.
- Every replay payload has identical shape to live service payload.
- Bundle opens on a clean machine without raw data or model source code.
- UI points to one replay root or one gateway URL only.

## 11. Final rehearsal and release

### IN-08: Run the delivery rehearsal

**Goal:** prove the system is usable, explainable, and recoverable under demo conditions.

### Rehearsal checklist

1. Start replay mode first. Confirm UI works without network.
2. Start consolidated service mode. Confirm live plan and simulation work on CPU.
3. Demonstrate one normal battle, one rule/eligibility transition, one constrained-energy decision, and one counterattack outcome.
4. Demonstrate the normal-race gate on a non-eligible state.
5. Verify model and rule versions in the UI footer.
6. Confirm every displayed quantity has correct provenance.
7. Confirm no overall-accuracy claim is shown.
8. Keep a checked replay bundle as rollback if live service fails.

### Release gates

- All IN-00 to IN-08 acceptance gates pass.
- No raw data, personal path, environment secret, or laptop address is required by the final bundle.
- No final artifact was trained or calibrated on British Grand Prix.
- UI uses one singular API surface.
- Documentation, release manifest, and replay bundle agree on versions.

## 13. Final definition of done

TrackShift is integrated only when it can take one decision-time StrategicState, apply the applicable rule snapshot, estimate state and uncertainty causally, remove illegal actions, evaluate feasible policy alternatives, return an explainable plan, simulate declared counterfactual policies, and serve all of this through one API or one replay bundle without depending on either developer laptop at runtime.
